# 小莹：人与人连接需求与续接记录

记录日期：2026-09-22。范围：本任务关于工具评估、生命成长、赠光、专属性、分享与表达辅助的讨论。

这是讨论基线和交接草案，不代表所有助手建议已获用户确认，不代表功能已经实现、合并或上线。后续收到用户修订时更新此文件，不新增相互矛盾的平行总结。

## 0. 接手先读

1. 产品中文名为「小莹」，英文名 The Living Wall。「碎光」可描述材质和历史原形，不再作为网站当前名称。
2. 用户明确希望线上成为短暂避风港：帮助人休息、恢复精力、获得启发，再促进人与人以及线下连接。减少孤独、促进生产力解放和缩小差距是长期愿景，不能写成软件已证明的效果或医疗疗效。
3. 当前优先验证「向具体朋友表达心意」；单纯增加一个会主动邀约的宠物，用户认为新鲜感与人本价值不足。
4. 用户强调节约 token、先小范围验证方向；先确认关键画面，再补完整互动和后台，避免反复搭大原型。
5. 不要把二版原型当成视觉验收通过；用户只进一步提出了按钮、入口与状态的可用性问题。
6. 原工作区有他人的未提交修改，分支较旧；不要切分支、重置或覆盖它，也不要以其中仍叫「碎光」的 PRD 推断线上名称。
7. 关联文档任务 [Issue #65](https://github.com/the-living-wall/The-Living-Wall/issues/65)。本轮功能尚未实现或部署；本地原型不具备真实跨设备分享与回声。

状态用语：
- **明确需求**：用户直接提出或明确认可的目标/约束。
- **建议方案**：助手已提出可落地设计，仍需在正式范围中确认；不能记成用户逐项批准。
- **待决**：会影响数据、费用、权限或验收的重要问题。
- **原型**：仅当前任务内可体验，不等于项目代码已实现。

## 1. 推荐优先级与交付顺序

本文件的 P0/P1/P2 是本轮新增工作的相对优先级，不重新定义仓库已有 P0。

### P0-A：修正现有原型的三个可用性问题

准备程度：问题已清楚，可立即做小范围修正；正式代码入库仍需 Issue。

- UI-01：留言编辑的「收起」实际是不保存，「就这样」实际是保存，语义不清。建议改为「取消」「保存留言」；保存后入口变为「编辑留言」。收件人的回声编辑必须使用「取消」「留下回声」等对应文案，不能混用保存留言。
- UI-01 补充（最新原型反馈）：回声紧接朋友留言呈现，标签和字重克制，编辑入口就近放置，避免散落在声音控件旁。入口用「回一句给朋友」说明对象；当前原型用「保存回声」并明确尚未发送，真正送达后再使用发送成功文案。
- UI-02：「换一种心意」太小、难发现。建议把当前心意整体做成可点击入口，加明确下拉标记，增大点击区域与文字层级。
- UI-03：当前左下角是固定提示，未接入生物状态。建议上行显示实际状态，下行保留操作提示；状态变化才更新，不逐帧跳字。右上是发送者的心意，左下是小莹的真实状态。
- 验收：用户不依赖解释即可分辨保存/取消；首次使用能发现心意切换；状态文字与实际行为相符，暂停时不继续报动作。

### P0-B：专属赠光的本地最小体验

准备程度：核心需求清楚，可先做本地体验；具体光迹表现与画面比例需人工验收。

- GF-01：一份心意面向一个具体的人，可填收件人昵称、发送者署名和留言；不要求实名或联系人权限。
- GF-02：发送者亲手留下简短光迹，作为个人印记；可以跳过，不要求画得像，不设置分数或完成任务。
- GF-03：接收画面必须能区分系统光体和用户印记。建议默认显示「这是小林为你亲手画下的一笔」；发送者可自愿解释图案。系统不擅自解释其情感含义。
- GF-04：建议按笔画顺序重现印记，再让小莹产生回应；不必录制视频。必须确实捕获用户笔画顺序才能宣称重现；自动示例笔画不能标成用户亲手绘制。
- GF-05：留言引导具体情境和共同经历，允许留白；不为增强专属感而编造故事。
- GF-06：朋友可观看、轻触、自愿回应，也可安静收下。没有已读、观看次数、停留时长或回复压力。
- GF-07：首版使用现有小莹光体，保留原站黑色沉浸空间、近白/淡青色层次、原字体与克制控件；完整画布居中呈现。留言和心意选择按需展开。
- 验收：创作者能留下自己的笔画和话；接收者能说清「谁为我留下了什么」；整页视觉经用户确认，真实成长档案不被改写。

### P0-C：真实链接与回声闭环

准备程度：用户已要求最小验证，核心流程清楚；以下技术路径是已解释的推荐方案，后台与数据规则仍需定稿。

最新执行边界（2026-09-22）：用户要求将发送者查看回复和主动提醒先记为待办，本轮只优化原型排版，不启动这些后续功能。以下优先级是规划顺序，不是当前开发授权。

- SH-01：建议复用现有网页，以 HTTPS 分享链接进入；用户自己复制到微信发送。优先于另建小程序。
- SH-02：推荐「一份正式发布的心意，一个固定 URL」。编辑草稿、打开、触摸、提交回声都不各建 URL；另一份新作品才生成新 URL。
- SH-03：推荐首版双方免注册、免手机号。公开随机链接与创作者管理凭证分离；凭证留在本机并可备份恢复。不能让公开 URL 获得管理权限。
- SH-04：跨设备保存作品与明确提交的回声需要真实持久化服务。原型同页状态或 localStorage 不能冒充跨设备功能。
- SH-05：保存作品参数、必要的印记形状数据和主动提交的文字，不上传真实成长档案、摄像头内容或高频原始互动轨迹。播放用的控制点与采样精度需在规格中界定。
- SH-06：创作者查看回声、关闭新回应、撤下/删除作品；收件人撤回自己的回声。范围源于前期最小闭环讨论，具体可逆性和状态转换须写入规格。
- SH-07：前期讨论目标为创作者在线约 5 秒内看到回声，离线后回来仍可查看；建议只在管理页可见时轮询，首版不做离线推送。
- SH-08：免登录不能验证留言者真实身份。持有公开链接的人均可能访问，转发后仍可打开。不能宣称只有指定昵称的人能看，也不能把匿名留言当成已验证的某位朋友。
- SH-09：微信和系统浏览器、本机与另一设备的管理记录不能假定互通；恢复凭证必须有可理解的入口。
- SH-10 **待办：发送者找回回复**。建议发送完成后保留「查看这份心意」，在本机首页提供「我送出的心意」入口；回访时提示「朋友给你留了一句话」。发送者通过自己的管理入口查看，不能用公开收件链接代替管理凭证。未返回网站就不知道有新回复，是第一阶段应明确的局限。
- SH-11 **待办：自愿主动提醒**。建议后续提供「收到回复时提醒我」，默认关闭；用户主动开启后，有新回复才通知，避免重复提醒。不显示已读未回，不催收件人回复。通知渠道、授权与退订方式、去重频率、隐私和费用尚待确定；本轮不申请权限、不接入通知服务。
- SH-12 **待办：补齐回复去向与反馈**。正式流程为接收者写话并明确「回复给朋友」，发送者回到原心意查看；提交成功或失败须真实反馈。当前原型的本页保存不能称为已送达，也不增加虚假的回复收件箱或通知演示。
- 验收：两个隔离浏览器身份完成发布、打开、留言、创作者读取与撤回/关闭等操作；刷新和服务重启后仍保留允许保存的数据；公开链接不能访问管理数据；微信真机验证视觉、触摸、声音。
- **实施前待决**：后台部署位置及费用；保存期限；删除/撤下/关闭的区别；发布后能否修改原作品；回声条数和频率上限及滥用处理；凭证丢失后的恢复边界。不要默认购买服务或扩大平台权限。

### P1-A：表达辅助，应紧接赠光闭环验证

准备程度：用户明确要求，应优先于新动物形态；交互可先用固定示例验证，真实 AI 调用需补模型、费用与数据约定。

- EX-01：帮助不知道如何开口、组织语言、表达关心的人。入口建议「不知道怎么说？一起想一句」。
- EX-02：输入几个词或一段草稿；复用用户已选的心意，仅补一个必要的情境问题，不做长问卷。
- EX-03：提供「自然一点」「短一点」「含蓄一点」「加一个轻邀请」等明确操作；每次两条建议，用户选择、编辑后采用。
- EX-04：保留原文，不直接覆盖；建议语气应容得下简短、幽默、含蓄等表达，不一律写成抒情模板。
- EX-05：保留真实称呼与情境；不编共同经历、不擅自承诺、不提高亲密程度、不用内疚或压力要求回应；由用户主动发送。
- EX-06：可选「为什么这样写」，帮助用户获得表达能力；「太肉麻」「太正式」「不像我」可作为本次修改反馈。
- EX-07：仅点击时调用，首版不边打字边生成，不自动读取聊天记录或通讯录。告知哪些文字会交给服务处理；作品保存最终采用版，服务侧日志/保留政策需另行确认。
- 验收：用户认为建议符合自己的本意；原文可恢复；无输入时不编故事；出错时可以继续手写；控制调用频率和费用，不自动发送。
- **实施前待决**：模型/供应商、成本上限、数据发送与日志边界、失败回退、是否提供每次/每日限额及如何提示。TypeSafe/Jev 的分类能力不能直接当成文案生成能力。

### P1-B：回声中的继续交流与轻量线下邀请

- 用户需求：有人不知道如何接话、维持交流。
- 建议入口：「帮我接一句」。用户主动选一段回声，并表明继续聊、约见面或先让对方休息。
- 可以建议自然结束，不把持续聊天时长作为成功指标。
- 「下次一起散步」等为自愿建议，不强制社交或承诺对方一定回应。
- 接收者在原印记旁补一笔、形成双方可区分的共创层，先记为下一步，不悄悄扩进 P0。

### P2：明确记录，暂不扩进首版

- LF-01 多形态：原碎片光体、白鲸（明确是海中的鲸，白鲸为示例）、海豚、小狗、宇宙光圈。早期还出现「金鱼」，后续对白鲸的澄清不能直接等同于删除金鱼；是否保留金鱼为待确认候选。
- LF-02 各形态的互动、不同阶段需求与用户选择。阶段数、解锁方式、行为差异和资源成本尚未定稿。
- LF-03 成长的新鲜感：用户质疑「谨慎接受→形成偏好→主动邀请」只是换了互动主动方；需要能够体现经历与人际关系的变化，不能把既有邀约换文案当成新成长机制。
- LF-04 整理长期形成的偏好：用户明确认为符合人本方向。记录哪些偏好、由谁确认、怎样查看/修改/删除、是否跨设备，均待决。不要默认推断人格或读取聊天历史。
- LF-05 共同经历影响小莹：早期规则未定；后续已明确优先朋友互动中的共同小莹，进入 CO-01～08 本地验证。当前确认边界见第 10 节，不再将模块归属与共同确认视为未决问题。
- PL-01 可选账号与跨设备作品管理；验证多次使用需求后再做。登录本身不等于获得成长档案云同步授权。
- PL-02 微信小程序、更完整的微信分享卡片：依赖平台接入及实际使用需求。不能以“做成小程序”替代后台设计。自愿离线提醒的待办与边界统一见 SH-11。
- PL-03 可选访问口令或指定收件人身份校验：解决访问范围，和情感专属性分开。昵称不能用于身份认证；不建议首次打开即永久锁定收件人。
- TL-01 TypeSafe/Jev：保留工具评估线索，暂不作为首版依赖。可后续评估将表达意图映射到既有视觉/节奏预设；不用于逐帧行为、成长数值、直接生成视觉/音频。具体 API、中文效果、价格与限额实施前重新查证。

## 4. 如何沉淀进项目

### 决策记录：保留完整讨论结论和未决项

本记录路径：`docs/decisions/2026-09-22-human-connection.md`。保留明确需求/建议/待决/证据/被否定方案，不粘贴全部聊天原文。它是后续接手的第一入口。

### PRD：只放产品基线、规划范围和真实实现状态

已新增「人与人连接」与「表达辅助」规划条目，概述目标、功能编号、首版/后续边界、隐私原则与验收目标，并链接决策记录。本轮 UI/GF/SH/EX/LF/PL/TL/DUAL 编号为规划索引，已检查不与当前 PRD 功能编号冲突。

不要把所有聊天原话直接追加 PRD；不要把“讨论已清楚”写成“已实现”。本次不得悄悄覆盖已有非目标。既有行为维持真实状态，新项注明规划中；实施 PR 再更新完成状态。

### Issue：一项可独立验收的工作一个任务

建议顺序：
1. 文档基线与范围确认。
2. 原型/界面可用性修正 UI-01/02/03。
3. 专属赠光本地体验 GF-01 至 GF-07（原站调性与手绘印记）。
4. 分享服务与免登录权限模型，随后完成两端回声闭环。
5. 表达辅助 MVP（可先独立做固定示例交互，再接真实模型）。

每项记录目标、范围、负责人、PRD 编号、依赖、验收及实际验证。部署或人工体验未完成，用 Refs，不提前关闭任务。

### OpenSpec：在开始真实行为/数据变更时使用

分享作品、权限凭证、回声与删除语义应使用 OpenSpec；AI 辅助的输入/费用/采用规则建议独立变更。明确文案修正可轻量 Issue+PR。不要为每个待办都建一个空规格，也不让用户学习工具命令。

### 稳定入口：让下一轮能找得到
