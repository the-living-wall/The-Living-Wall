# 深度输入延迟：软件对照与现场验收

关联 [Issue #89](https://github.com/the-living-wall/The-Living-Wall/issues/89)、#50、#25；功能 IN-03、HW-02。方案见 [OpenSpec](../../../openspec/changes/reduce-depth-input-latency/)。本轮仅本地实验，不发布生产，现场验收未完成。

## 已测结果（2026-09-23）

旧基线为 `bffc5a18cf642d347c0a0f05b34920b56ef0c4ce`；优化版本为本 PR 的实现。环境：Apple Silicon Mac、Node 24.21.0、Chrome 153.0.8010.53、1280×800、前台无头浏览器、本机开发服务。网页网络拦截器生成 30fps 的不同位置帧，每次回复另等 5ms；没有相机、真实管道或投影设备参与。这能验证网页调度改善，不能证明整个硬件链路达标。

- [优化前原始数值](baseline.json)：10.007s 内圆圈发生 94 次不同位置更新，观测频率 **9.30 次/秒**。
- [优化后原始数值及诊断导出](optimized.json)：10.012s 内圆圈发生 301 次不同位置更新，观测频率 **30.00 次/秒**。诊断窗口 10.051s，301 个唯一有效位置帧，**29.95 帧/秒**、0 掉点。
- 优化后模拟链路的 DOM 提交帧龄保守估计 P95 **37.56ms**，请求往返 P95 **7.60ms**，更新间隔 P95 **34.80ms**。模拟处理耗时固定 1ms，不能作为真实检测性能结论。旧版没有接收时间诊断，不能给出其同口径 P95。
- 浏览器重复冻结帧测试观测到约 **332ms** 内消失（包含预等待；自动化观察有调度误差），确定性时钟测试验证按源帧龄与完整往返时间扣减 300ms 有效期。慢请求、校准、无区域、旧协议、服务会话切换、两轴镜像、退出时迟到响应、普通成长档案隔离均验证。

频率按圆圈样式变化的 rAF 观测计算，`(N−1)/(最后一次−第一次)`；JSON 诊断按记录窗口 `N/窗口时长`，两者分母不同。原始圆圈与光团自身缓动分开。DOM 提交不是显示器或投影仪发光时刻，不能用该 P95 替代物理响应。

复现优化后测试：启动本分支开发服务后，运行 `node scripts/depth-latency-browser-qa.mjs http://127.0.0.1:3098/ /tmp/depth-optimized.json`（需安装 Chrome）。脚本只输出数值 JSON，不录影、不打开摄像头。旧基线在修改前采用相同 30fps/5ms 输入、10 秒 rAF 样式观测；原记录保留，不通过新版本伪造基线。

## 检查与失败记录

- 前端单元测试、类型检查、lint、构建、Python 流水线/检测/前端契约测试、引导页测试与 OpenSpec 严格校验，最终结果见 PR 的最新检查记录。
- 第一次旧版浏览器基线未等待页面完成 hydration，点击后超时；加 2 秒等待后完成。没有将超时样本计入成功基线。
- 初次优化后浏览器测试在存档断言失败：进入深度模式会合法创建当前普通存档，测试把“未创建”误当成应一直不存在。改为进入模式后取普通存档基线，再对比实验结束；实现未为此修改成长规则。
- 初次 lint 发现诊断 UI 在渲染期读可变引用/时钟，后改为事件更新视图状态；后续新增测试的 URL 类型警告也已修正。
- 本机 NumPy/OpenCV 环境在原有 `detector.py` 平面矩阵运算处输出 divide-by-zero/overflow/invalid RuntimeWarning，测试仍通过。本轮未改检测算法，不把警告描述为已修复。OpenSpec 对既有 `local-sound-events` 变更提示归档目标缺失；本变更校验通过，未归档其他变更。

用户报告 Gemini **355**，原服务适配 **335**；本次保留现有硬件选择边界，错误提示会列出 SDK 枚举型号，不将两型号视为相同。若现场确为 355 且现有选择不支持，应另查其 SDK 流配置与兼容性，不能将“未能连接”计作低延迟验收通过。

## 现场记录与验收（全部待完成）

先固定同一电脑、相机位置、距离、选区、光照与 50mm 规则，记录测试提交 SHA、完整启动命令、操作系统/浏览器、SDK 枚举型号、深度分辨率、配置 fps、实测 `capture_fps`、USB 连接类型、投影型号/连接方式/刷新率。`/api/input.device` 提供 SDK 型号、宽高、配置 fps、连接类型与 SDK 帧号/时间；网页诊断提供采集/处理/预览计数及覆盖数。没有返回的硬件参数如实填“未知”，通过系统或设备设置另查，不从产品名称推算。

按电脑屏幕 → HDMI/USB-C 有线 O3 → AirPlay 的顺序，各做优化前/后三轮、每轮一分钟。每轮包含水平/垂直移动、急停、反向、移开与重入；每次重新启动或移动相机都重新采集 30 张不同新帧校准空墙。记录光团缓动、坐标偏差、离开近墙范围导致的失效，单独解释，不算成识别延迟。

1. 新版开启“输入诊断”→“记录 60 秒”→“导出数值”，同时保存上述环境记录。旧版按外部数值/同框录像测量；没有诊断字段则注明缺测。
2. 稳定 30fps 且有有效近墙输入的窗口，至少 25 个不同位置帧/秒；有意移开时段单列，不能把空墙时间当成降帧。SDK接收至 DOM 提交保守 P95 ≤100ms。JSON `display_submit_age_upper_ms = source_age_ms + 完整请求往返 + 响应至DOM提交等待`；Python 同机单调时钟跨采集/服务传递，浏览器只叠加时间段，不减不同进程的时钟。SDK曝光/内部缓存不在该起点内。
3. 测量时保留普通实验界面（“全屏纯画面”会隐藏原始圆圈）。用同画面录像同时拍到手部动作与原始绿色圆圈，对每次动作变化标记起始帧与响应帧，以录像时间戳之差计算延迟和 P95。有线目标 P95 ≤150ms；记录视频实际 fps、时间分辨率（30fps约33.3ms、60fps约16.7ms；变帧率用时间戳）和有效事件数。此步骤由现场操作者主动录像，不由诊断程序保存影像。
4. 停止采集/断开输入，测量最后有效帧至圆圈清除，目标 ≤350ms；无效/无区域/校准中立即停止。对比掉点次数与覆盖数量，不以更多丢失有效互动换取低延迟。不同连接的显示延迟不能用 USB 或网页指标代替。
5. 未达标保留全部失败轮次，按采集速率、源帧龄、检测、请求往返、DOM 提交、物理显示依次定位；不扩大区域、放宽有效性或改光团性格。用户确认现场结果后再关闭 Issue #89。
